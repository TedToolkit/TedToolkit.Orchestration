# Declaration-only pipelines

Status: Accepted and implemented. Owner: library maintainers. User-approved direction: 2026-09-04.

A named partial class explicitly inherits Pipeline and overrides Configuration(Pipeline.Builder). Inheritance from the actual runtime symbol, directly or through an intermediate base, is required for generation. Generated partial declarations never add a base type. Unrelated configuration methods are ignored. Builder, StepBuilder and StepArgument are empty readonly markers. Each valid local Step receives a generated extension method. Configuration is analyzed as source and never invoked by generated code. Legacy Configure(Builder, ...) remains supported: extra parameters become typed constructor-input fields.

The generator emits a private Run method for each registration. Constants are mirrored directly; other argument expressions are evaluated once when the Step becomes ready, in original argument order. Required local initializers run once per consuming Step, in declaration order. A local used by several Steps is evaluated separately for each consumer; use an upstream Step for shared computation. Unused locals do not execute. Standalone executable statements, local functions, mutable/ref locals and dynamic graphs are rejected rather than silently discarded. Class helper methods may contain ordinary behavior.

Each registration method directly creates the business ref struct Step for every attempt. Evaluated arguments and resolved services stay in local variables outside the retry loop. Synchronous disposal finishes before success or retry. Async execution obtains and awaits the business task without retaining the ref struct. Constructor wrapper types, constructor interfaces and delegates are unnecessary.

Pipeline supplies StepAttempt to own the retry budget, cooperative timeout resources and failure decisions for one Step invocation. The generated loop uses while (attempt.Begin()). Begin returns false after success or starts a fresh attempt after a retryable failure. RetryOrThrow applies cancellation precedence, timeout translation and the retry budget. It records only retryable failures and immediately rethrows a terminal failure while preserving its original stack. A single using scope disposes the final timeout source. The generated Step method owns the loop and construction. Argument failures happen before retry handling. Default policies emit no loop or timeout source. Cleanup completes before retrying; caller cancellation wins and is never retried.

All-synchronous graphs, including empty graphs, generate Results Execute and void ExecuteWithoutResults. Failures propagate synchronously. Graphs with any asynchronous Step generate Task<Results> ExecuteAsync and Task ExecuteWithoutResultsAsync. Every entry point uses direct Step calls without local functions or exception wrappers. Parallel graphs retain one typed task per Step. Generated Step methods receive and await their own upstream tasks before evaluating arguments or starting business work. These tasks were already started in Execute; reading them in argument order does not serialize their business execution. No inner WhenAll is needed because the outer wait owns draining. There are no branch methods or execution segments. Execute directly owns a linked CancellationTokenSource. Parallel Step methods receive only that source; its linked token observes external cancellation. Each terminal Step failure signals cancellation and rethrows the original exception without restoring the caller token; the outer non-generic Task.WhenAll drains every started task. There is no separate ParallelExecution state object or CompleteAsync wrapper. Concurrent exception selection follows Task.WhenAll with no additional ordering guarantee; invocation-wide caller cancellation no longer overrides all concurrent faults. Recoverable Step failures remain inside StepAttempt. Cancellation callback exceptions cannot replace the original failure. Synchronous Steps in parallel graphs use async task-returning methods for dependency coordination, without Task.Run; this may allocate more tasks than the former segment-based design.
No IConfiguration, configuration Capture method, capture cursor, runtime graph or generated Builder is needed. The tradeoff is declaration-only semantics: Configuration cannot be used as a constructor-time hook. The class or override must be sealed so a later override cannot replace the graph source. Generic/nested pipelines and explicit constructors remain unsupported.

Source generation cannot erase handwritten methods from an ordinary assembly. Removing all generated references lets ILLink remove Configuration during trimmed publication. The runtime is marked IsTrimmable and the Playground enables PublishTrimmed. Verification publishes a self-contained Release application with TrimMode=link, checks both assembly metadata tables for absent Configuration/Configure methods, and runs the trimmed executable. Consumer reflection roots or explicit calls can retain the method.

Verification covers argument timing, retries reusing values, named-argument and local-initializer order, aliases and extension expressions, explicit conversions, diagnostics, all four Step contracts, DI, disposal, cancellation, timeout, concurrency and completion-only allocation behavior. Historical benchmarks remain historical evidence.


Policy-free serial async Step methods return the original business Task through ObserveStepAsync whenever no cancelable observation is required. Pending cancelable tasks use a shared observer to preserve completion/cleanup and token semantics. Policy loops and parallel Step methods keep their necessary async state. Redundant per-Step cancellation checks in the serial entry were removed; Step methods continue to enforce checks. The outer parallel WhenAll is explicitly non-generic so it does not allocate an unused result array when every Step returns the same type.
